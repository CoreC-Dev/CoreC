## 1. 实测发现清单（按严重度排序）

以下均为**部署实例上实测观察**，证据可复现：

### F1【严重】宿主机挂起恢复后引擎静默卡死 + 锁逐步扩散

**场景**：宿主机长时间挂起（本例 ~11 小时，S3 睡眠/宿主冻结/长网络分区同类）后恢复。
**实测表现**（edge-1 与 corec-local 双双命中，两者都读 sim-a）：
- 驱动读取**静默冻结**：所有驱动点时间戳停在恢复前的时刻（temp_01 冻结于 13:19:44，此后 12 小时不更新）
- **无任何错误日志**、无重连日志、无 panic——`timeout: 3s` 配置形同虚设，goroutine 卡死在无超时保护的路径上
- **API 渐进式锁死**：`GET /drivers` → `GET /stats` → `GET /healthz/ready` 相继挂起（>120s 无响应），而 `GET /tags`、`GET /healthz/live` 正常应答——**存活探针说谎**，容器状态 Up、Docker 不重启、LB 不摘除节点：**静默半死**是生产事故的标准形态
- 派生评估器（纯计算无 I/O）照常运行：持续产出 bad-quality 点（源失鲜），**仪表盘满屏标红**——用户看到的"很多错误"的直接来源之一

**初步归因方向**：modbus 客户端在 TCP 半开连接上的某条调用路径未被 3s 超时覆盖（read deadline 未覆盖到卡死点，或重连循环持锁等待）；/stats、/ready、/drivers 与卡死路径存在锁交集。**修复必须包含**：① 所有设备 I/O 路径的超时全覆盖（含重连路径）；② 锁持有期间的 I/O 禁止（先拷贝后 I/O）；③ healthz/live 的诚实化（或 ready 的强制化：编排系统用 ready 而非 live）。

### F2【高】演示配置生成器地址 bug（本次部署的坏数据来源）

`gen.py` 对 ro_10/11/12 生成了 4 位地址 `"3010"/"3011"/"3012"`——不在输入寄存器区间（30001+），被地址解析器落入**线圈区间**（coil 3010），读取必然失败；缓存停留在启动种子值（`type:"bool"` 来自线圈区推断、value null、quality 1、时间戳冻结在启动时刻）。三份 edge 配置 + local 双驱动全部命中。
**修复**：生成器改为 5 位零填充；重新生成配置并重启受影响实例。**顺带的正面发现**：地址解析器对 4 位数字静默落入线圈区而非报错——考虑对"意图为 3xxxx/4xxxx 但位数不足"的地址给出校验警告（配置校验钩子 #25 可覆盖）。

### F3【中】派生标签的质量恢复语义（行为正确但可观测性缺陷）

派生标签在源失鲜（stale-guard 30s）时正确产出 bad-quality 点；但**12 小时过去，值持续更新、质量永远卡在 bad**——对运维人员，"源失鲜"与"派生自身坏了"不可区分。生产改进方向：bad-quality 的派生点在元数据中标注原因（stale-sources vs eval-error vs missing），或提供 per-derived 的源新鲜度 API。

### F4【低】/drivers/{name}/tags 曾观测到 60s+ 挂起（后来 68ms 恢复）

在 F1 锁扩散的时间窗内，该端点先挂后恢复。若 F1 修复后不再复现则并入 F1 关闭；否则单独追查该 handler 的锁路径。

### 已排除的"看似错误"（写入文档防误判）

- edge-2 的 `WARN msg=ALERT`：spiky 模拟器每 45s 越限触发告警规则——**设计行为**，是告警系统的正确输出
- 网关扁平 `/tags` 只显示每驱动同名标签之一：**已记录的平铺冲突语义**，用 `?driver=` 过滤查看（见 PIPE-2）
- REST `/write` 失败不进死信队列：死信是命令通道（MQTT 下行）语义；REST 直写同步返回失败并记审计——文档已如此声明

### C. 稳定性维度

- **锁死检测**（F1 直接产物）：全 API 端点在故障注入下的可用性矩阵；任何端点 >5s 无响应即 fail
- **资源**：容器内存/Goroutine 数/Prometheus 指标在 soak 前后对比（pprof 采样）
- **日志纪律**：稳态 ERROR=0（WARN 仅告警语义）；同一错误节流不刷屏
- **崩溃韧性**：SIGTERM 优雅关停排空数据；双信号强杀行为已文档化

### D. 仪表盘可用性（用户直接体感）

## 3. 验收标准（生产级定义）

1. **B3 通过**是本程序的一号验收：宿主挂起恢复后，要么采集在 ≤2 个采集周期内自动恢复，要么 ready 诚实翻红且 API 全端点不挂（>5s 无响应视为挂死）
2. B1–B10 全部工况下：**任何 API 端点不得无响应挂起**；进程不得崩溃（B1 既有回归保持）
3. 稳态 4h soak：内存增长 <10%、goroutine 净增 <5、错误日志 =0
4. A1–A18 功能全过（含边界：128 批上限、422 全败、只读拒绝）
5. 仪表盘走查零 P0/P1 体验缺陷（坏点有解释、断流有提示）
